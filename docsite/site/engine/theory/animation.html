Animation

A 2D character is a spritesheet and a rule for which part of it to show. Animation is that rule, kept out of gameplay code.

The concept

Sprite animation is flipbook playback: a list of frames (rectangles on a spritesheet) shown one after another, each for a short time. Playing one clip is easy. The hard part is choosing the clip: idle becomes run when the player moves, run becomes attack on a button press, attack returns to idle when it finishes. Written as if chains in gameplay code, that logic spreads and breaks.

State machines

Engines model it as a state machine: each state plays one clip, and transitions between states fire on conditions. Gameplay code stops saying "play run" and only reports facts; the machine decides. The facts come in two kinds:

  • Flags are persistent conditions that stay true until changed ("running").
  • Triggers are one-shot events ("attack pressed") that wait until a transition consumes them, so a press is never lost or handled twice.

Ending, priority and direction

A clip needs a rule for its last frame: loop, freeze on it, or give the sprite back its original image. Transitions are tested in priority order, so "hurt" can override everything else. And a character that walks in several directions needs one set of frames per direction, chosen from the way it is facing.

How ASGE does it

Three assets, one component

The data is split so each piece is reused independently:

  • A FrameTable (TOML) is the list of source rects for one clip, as described on Assets.
  • An asset::AnimationStateMachine (.animsm XML) declares the flags, triggers, clip names, states and transitions. Up to 32 flags and 32 triggers, each a bit of a mask.
  • An asset::AnimationClipSet (.animset XML) names its machine and binds each clip name to its frame table(s) and a frame duration.

A components::Animator stores only the clip set path, a playback speed and a start-playing flag; those are what a scene file saves. AssetManager::ResolveAssets loads the set, its machine and the frame tables once, shared by every animator that names them. Until then SetFlag and Fire do nothing and return false. Everything else on the component (state, frame, flags, triggers, heading) is runtime state.

player.animsm
<AnimStateMachine initial="idle">
  <Flags><Flag name="running"/></Flags>
  <Triggers><Trigger name="attack"/><Trigger name="hurt"/></Triggers>
  <Clips><Clip name="idle"/><Clip name="run"/><Clip name="attack"/><Clip name="hurt"/></Clips>

  <State name="idle" clip="idle" end="loop">
    <Transition to="hurt"   trigger="hurt" priority="10"/>
    <Transition to="attack" trigger="attack"/>
    <Transition to="run"    when="running"/>
  </State>
  <State name="attack" clip="attack" end="hold">
    <Transition to="run"  atEnd="true" when="running" priority="1"/>
    <Transition to="idle" atEnd="true"/>
  </State>
  <!-- run and hurt omitted -->
</AnimStateMachine>

What a frame of AnimatorSystem does

systems::AnimatorSystem visits every entity with an Animator and a Sprite. For each one, in order:

  1. Update the heading from a moving PathFollow, else a nonzero Velocity, else keep the last one.
  2. Start on first sight: enter the machine's initial state, or stay stopped if m_StartPlaying is false.
  3. Advance time by dt times the playback speed, stepping through frames whose duration (the frame table's own, else the clip's) has elapsed.
  4. Try transitions when something changed: the first transition of the current state, highest priority first, whose conditions hold is taken and its trigger consumed.
  5. Write the frame into Sprite::m_SourceRect.

The animator never draws anything: RenderSystem just sees whatever source rect was last written. RenderPipeline runs AnimatorSystem, CameraSystem then RenderSystem in that order.

Transitions and end modes

A transition can require flags to be set (when="running") or clear (when="!running"), a pending trigger, and optionally that the clip has finished (atEnd). A state's end picks what happens on its last frame:

  • loop wraps to the first frame.
  • hold stays on the last frame and marks the animator finished; an atEnd transition can then leave.
  • restore gives the sprite its original source rect back.

Each finished playback emits events::OnAnimationFinished() with the entity, a signal gameplay code can connect to. While playing, the animator owns the sprite's source rect; Stop releases it and Resume takes it back.

Directional clips

Instead of a path, a clip of the clip set can hold 1 to 8 <Variant path> children, one frame table per direction, spread evenly clockwise from north: four variants are N/E/S/W, eight add the diagonals. All variants share the clip's frame duration. Animator::m_Heading (a screen-space vector, south until set) picks the nearest one; a small hysteresis stops a heading sitting on a boundary from flickering. A heading change swaps the frame table without restarting the clip, so the walk cycle keeps its frame. Set the heading by hand with components::SetHeading; a zero vector is ignored, so an entity that stops keeps facing the way it moved.

hero.animset
<AnimClipSet machine="anim/humanoid.animsm">
  <Clip name="run" frameDuration="0.10">
    <Variant path="anim/hero_run_n.toml"/>
    <Variant path="anim/hero_run_e.toml"/>
    <Variant path="anim/hero_run_s.toml"/>
    <Variant path="anim/hero_run_w.toml"/>
  </Clip>
  <Clip name="death" path="anim/hero_death.toml" frameDuration="0.10"/>
</AnimClipSet>
animator.cpp
SetFlag( animator, "running", moving );          // persistent: keeps its value until set again
if ( attackPressed ) Fire( animator, "attack" ); // one-shot: consumed by the transition that listens
