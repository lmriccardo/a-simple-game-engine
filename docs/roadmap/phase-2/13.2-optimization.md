# Optimization — Phase 2

*Priority: Tier 4, but continuous — a deep pass waits for real content to profile.
See [README](../README.md). Other phases:
[Phase 1](../phase-1/13.1-optimization.md) (CPU profiling — done),
[Phase 3](../phase-3/13.3-optimization.md) (streaming, ECS cache optimization).*

## Goals
GPU-side profiling, and a job system for parallelizing work across cores.

## Current state
The job-system building block already exists: [01-Core Engine](../phase-1/01.1-core-engine.md)'s
`ThreadPool` ([ThreadPool.hpp](../../../src/ASGE/Core/Concurrent/ThreadPool.hpp))
already provides a worker-pool + job queue. This phase's "job system" task is about
using it for engine workloads (asset loading, parallel ECS systems), not building a
new one — see [03-ECS Phase 2](03.2-entity-component-system.md)'s parallel
system execution and [05-Asset Pipeline Phase 2](05.2-asset-pipeline.md)'s
async loading, both of which are meant to build on this same `ThreadPool`.

## Design notes
GPU profiling only matters once `SDLRenderer` draw calls are numerous/complex
enough for GPU time to be a real bottleneck — nothing currently in this engine
justifies it. Revisit once [10-Rendering System](../phase-1/10.1-rendering-system.md) Step 1
or later steps land.

## Tasks
- [ ] GPU frame-time profiling, once `SDLRenderer` usage is complex enough to
      justify it
- [ ] Confirm/document `ThreadPool` as the shared job-system backend for
      [03-ECS Phase 2](03.2-entity-component-system.md) and
      [05-Asset Pipeline Phase 2](05.2-asset-pipeline.md), rather than each
      building its own

## Deliverables
- GPU timing visible alongside `TimingProfiler`'s CPU timing, once needed
- At least one real workload (parallel ECS systems, or async asset loading) running
  on `ThreadPool`, proving it as the shared job-system backend

## Explicitly out of scope
Streaming optimizations, ECS cache optimization — see
[Phase 3](../phase-3/13.3-optimization.md).
