# Input System — Phase 2

*Priority: Tier 1 stretch — not MVP-blocking. See [README](../README.md). Other phases:
[Phase 1](../phase-1/04.1-input-system.md) (done: keyboard, mouse, polling),
[Phase 3](../phase-3/04.3-input-system.md) (touch).*

## Goals
Gamepad support, and remapping/action-maps once there's a second physical input
scheme to justify the abstraction.

## Design notes
- **Gamepad support is a separate SDL subsystem** (`SDL_gamepad.h`, already vendored
  under `third-party/SDL`) with its own connect/disconnect lifecycle — not an
  extension of the keyboard/mouse event shapes from
  [Phase 1](../phase-1/04.1-input-system.md). It needs its own `SystemEventType`,
  event structs (button, axis, connect/disconnect), and `SDL_TranslationUnit`
  entries, following the same pattern mouse translation used.
- **No rebinding/action-map system until there's a second control scheme to map.**
  Building a generic action-map abstraction against a single hardcoded WASD scheme
  would be guessing at requirements; do it once gamepad support gives the engine two
  physical input sources that plausibly need to map to the same logical action
  (e.g. "move" bound to both WASD and a left stick).

## Tasks
- [ ] Gamepad `SystemEventType` + event structs (button press/release, axis motion,
      connect/disconnect)
- [ ] SDL gamepad translation (`SDL_EVENT_GAMEPAD_*` → asge events)
- [ ] `InputState` gamepad queries, mirroring the keyboard/mouse shape
      (`IsButtonDown`/`Pressed`/`Released`, axis value accessors)
- [ ] Action-map abstraction: named logical actions bound to one or more physical
      inputs (key, mouse button, gamepad button/axis)
- [ ] Rebinding: a way to change an action's bound input(s) at runtime

## Deliverables
- Gamepad connect/disconnect + button/axis events flowing through the same
  `SystemEvent` pipeline as keyboard/mouse
- `InputState` gamepad queries
- An action-map API translating a logical action name into "is any of its bound
  inputs currently active"

## Explicitly out of scope
Touch input — see [Phase 3](../phase-3/04.3-input-system.md). Force feedback/haptics,
gamepad-specific UI glyphs (button icon prompts) — no concrete feature needs them yet.
