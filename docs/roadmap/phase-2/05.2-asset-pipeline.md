# Asset Pipeline — Phase 2

*Priority: Tier 1 follow-on — worth doing once real content makes load times/memory
visible. See [README](../README.md). Other phases:
[Phase 1](../phase-1/05.1-asset-pipeline.md) (asset-handle concept),
[Phase 3](../phase-3/05.3-asset-pipeline.md) (live reload).*

## Goals
Stop reloading and re-decoding the same asset every time it's referenced, and stop
blocking the main loop while a large asset decodes.

## Design notes
- **Caching** keyed by the asset-handle's path (from [Phase 1](../phase-1/05.1-asset-pipeline.md))
  — a second reference to the same path returns the already-loaded value instead of
  re-decoding. Only useful once something actually loads the same asset twice; no
  current example does.
- **Async streaming** needs somewhere to run the decode off the main thread —
  [01-Core Engine](../phase-1/01.1-core-engine.md)'s existing `ThreadPool`
  (`Core/Concurrent/ThreadPool.hpp`) is the natural fit, avoiding a second thread-pool
  implementation just for asset loading.

## Tasks

- At least one asset type loadable asynchronously without blocking the frame loop
