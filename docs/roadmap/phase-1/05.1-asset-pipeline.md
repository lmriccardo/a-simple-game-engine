# Asset Pipeline — Phase 1

*Priority: Tier 1 — moved up ahead of Scene Management. See [README](../README.md).
Other phases: [Phase 2](../phase-2/05.2-asset-pipeline.md) (caching, async streaming),
[Phase 3](../phase-3/05.3-asset-pipeline.md) (live reload).*

## Goals
Formalize a common asset-handle concept before a third ad-hoc loader (audio) shows
up and triplicates the pattern, and before [06-Scene Management](06.1-scene-management.md)/
ECS need a way to reference assets by handle rather than a hardcoded path per demo.

## Current state
Two independent, hand-rolled loaders already exist and already do the "Basic tier"
job for their own asset type: `Image::Load(Path)`
([Image.hpp](../../../src/ASGE/Core/Graphics/Image.hpp)) and
`Font::Load(Path, pixelHeight)` ([Font.hpp](../../../src/ASGE/Core/Graphics/Font.hpp)),
both returning a `Result<T>`. There is no shared concept between them — each example
calls its own loader directly with a hardcoded path (see `LoadTexture`/`LoadFont`
helpers in `texture_demo`/`text_demo`). Nothing resembling metadata, an asset
database, or async loading exists.

Every path that reaches a loader today is a raw OS path handed straight to
`filesystem::ReadText`/`ReadBinary`/`Copy`
([FileIO.hpp](../../../src/ASGE/Core/Filesystem/FileIO.hpp)) — there is no
indirection between "the path an asset is known by" and "where it actually sits on
disk". Each example bakes in its own relative-to-CWD path, which only works because
the demo binary happens to run from a directory next to its assets.

## Design notes
- **Unify the existing pattern, don't replace it.** `Image::Load`/`Font::Load`
  already work and are tested; Phase 1 is about extracting the common shape (a
  `filesystem::Path` in, a `Result<T>` out) into something `AudioClip::Load` (once
  [08-Audio](08.1-audio-system.md) exists) can follow too, not rewriting either loader.
- **Asset references, not an asset database.** The concrete need right now is: let
  ECS components ([03-ECS](03.1-entity-component-system.md)'s `Sprite`/`AudioSource`)
  and future scenes ([06-Scene Management](06.1-scene-management.md)) hold a handle to
  an asset instead of a hardcoded path baked into example code. A full metadata
  system / compression / searchable asset database is scope creep from the original
  generic-engine template — nothing here has enough assets yet to need it.
- **`filesystem::Path`/`FileIO` already exist** ([01-Core Engine](01.1-core-engine.md))
  as the underlying file-access layer every loader already builds on — Phase 1 adds a
  handle/reference concept on top, not a new I/O layer underneath.
- **A thin Virtual File System sits between the handle and `FileIO`.** An asset
  reference should carry a *virtual* path (e.g. `"textures/hero.png"`), not the raw
  OS path baked into today's examples. The VFS mounts one or more real directories
  under a virtual root and resolves a virtual path to the first matching real
  `filesystem::Path`, in mount order — letting an override/mod directory be mounted
  ahead of the base assets directory later without touching any loader or handle
  code. It is deliberately just a mount table + resolver on top of the existing
  `FileIO`: no archive/pak format, no compression, no packaging step — those are
  scope creep the same way a full asset database is (see below).
- **Resolve-then-load, don't change what `Image::Load`/`Font::Load` do with a path
  once they have one.** The VFS only replaces "hardcoded OS path" with "virtual path
  resolved via the VFS" at the point the asset-handle layer calls into the existing
  loaders; the loaders keep taking a `filesystem::Path` and calling `FileIO` exactly
  as they do today.

## Tasks
- [x] A minimal Virtual File System: mount a real directory under a virtual root,
      and resolve a virtual path to a real `filesystem::Path` by walking mounts in
      order, returning a `Result<Path>`-shaped not-found error when nothing matches
- [ ] A common asset-handle type (e.g. `Asset<T>` or similar) wrapping "loaded value
      + the virtual path it came from", built from the shape `Image::Load`/`Font::Load`
      already share, resolving through the VFS before calling the existing loader
- [ ] Asset references usable from ECS components instead of a raw path per demo

## Deliverables
- A minimal VFS: mounting a directory and resolving a virtual path against it
  returns the right real path, and an unmounted/unknown virtual path returns an
  error instead of touching the filesystem
- A shared asset-handle concept that `Image::Load`/`Font::Load` (and eventually
  audio) all produce, referencing assets by virtual path
- At least one ECS component or example referencing an asset by handle instead of a
  hardcoded path

## Explicitly out of scope for Phase 1
Caching and async streaming ([Phase 2](../phase-2/05.2-asset-pipeline.md)), live
reload ([Phase 3](../phase-3/05.3-asset-pipeline.md)), and a full
metadata/compression/database system — no concrete requirement for any of it yet.
The VFS itself stays a mount table + resolver: no archive/pak format and no
override-priority rules beyond mount order — revisit only once a real mod/override
use case shows up.
