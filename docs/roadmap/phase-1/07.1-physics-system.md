# Physics System — Phase 1

*Priority: Tier 2 — first system that makes gameplay feel like gameplay.
See [README](../README.md). Other phases:
[Phase 2](../phase-2/07.2-physics-system.md) (CCD, raycasts, character controller),
[Phase 3](../phase-3/07.3-physics-system.md) (soft body, vehicle physics).*

## Goals
Basic 2D collision and gravity — enough that entities can bump into each other and
fall, without a general-purpose 2D physics engine.

## Current state
Done. Collision detection and response exist and are tested, gravity is
wired up, and one entry point runs all of it in the right order. A
`Collider`'s shape is a `Rect` or a `Circle`
(`ColliderShape = std::variant<Rect, Circle>` —
[Game/Components/Collider.hpp](../../../src/ASGE/Game/Components/Collider.hpp));
`math::AabbOverlap`/`CircleOverlap`/`PenetrationVector`
([Core/Math/Geometry/Collision.hpp](../../../src/ASGE/Core/Math/Geometry/Collision.hpp))
cover every shape pairing, dispatched via `std::visit`. `Rigidbody`
([Game/Components/Rigidbody.hpp](../../../src/ASGE/Game/Components/Rigidbody.hpp))
now exists — `m_Mass` plus an `m_AffectedByGravity` flag — as the
physics-driven marker `03-ECS`'s component catalog anticipated, orthogonal to
the pre-existing `Velocity` component rather than replacing it.

Each `Collider` also carries a `ResolutionType` (`Solid`/`Trigger`/`Unknown`,
defaulting to `Solid`). `systems::DetectCollisions`
([Game/Systems/PhysicsSystem.cpp](../../../src/ASGE/Game/Systems/PhysicsSystem.cpp))
finds every overlapping `Transform`+`Collider` pair each frame as a
`CollisionContact` (both entities, the penetration vector, whether either
side is a `Trigger` — a `Trigger` is always reported as the contact's first
entity, regardless of which one it actually found first); a pair with
`Unknown` on either side is skipped entirely, not reported as a contact at
all. `systems::ResolveCollisions` pushes apart every non-`Trigger` contact:
an entity only counts as movable if it has both `Velocity` and `Rigidbody`
(anything missing either — e.g. static level geometry — is immovable), and
when both overlapping entities are movable the correction is split by mass
ratio (the heavier body yields less) rather than evenly, zeroing velocity on
whichever axis was corrected. `systems::DispatchTriggerEvents` fires
`events::OnCollisionTriggerEnter`/`Stay`/`Exit`
([Game/Events.hpp](../../../src/ASGE/Game/Events.hpp)) for every `Trigger`
contact — a small `PhysicsState` (last frame's overlapping pairs) is what
lets it tell a new overlap (Enter) from a continuing one (Stay) from one
that just ended (Exit, including when that's because one side was
destroyed rather than moved away) — a non-blocking sensor for
pickups/hazards/goal-zone gameplay.

Each `Collider` also carries a `CollisionLayer m_Layer`/`m_Mask` pair
(`CollisionLayer = std::uint32_t`, `m_Layer` defaulting to `1`, `m_Mask`
defaulting to every bit set — i.e. "collides with everything" unless told
otherwise). `components::details::LayersCanCollide` checks both directions
(`inA.m_Layer & inB.m_Mask` and `inB.m_Layer & inA.m_Mask`, both non-zero) —
`DetectCollisions` runs it first, before any shape overlap test, so an
excluded pair is skipped just as completely as an `Unknown` one, Solid or
Trigger. `examples/physics_demo` demonstrates it with two boxes on
mutually-exclusive layers that fall straight through each other while both
still land on the floor normally.

`systems::GravitySystem` (same file) adds a constant acceleration to `m_DY`
each frame for every `Rigidbody`+`Velocity` entity whose
`m_AffectedByGravity` is true. `systems::MovementSystem` (plain
velocity-integration) is unchanged. `systems::PhysicsUpdate` wires all of the
above together in the right order (gravity, movement, detect, resolve,
dispatch) — the one entry point a game loop actually needs.
`examples/physics_demo` calls just that, once per frame, and demonstrates
the whole system together — a static floor/walls, a falling/settling stack
of mass-varied boxes, a Trigger despawn zone, click-to-spawn, reset.

## Design notes
- **Rect and Circle, not arbitrary/rotated shapes.** Matches this engine's 2D
  scope ([00-overview](../00-overview.md)) — axis-aligned boxes and circles
  cover the common 2D gameplay case (platformers, top-down, anything roughly
  round) without the complexity of a general narrowphase for rotated/convex
  polygons.
- **A system, not a class hierarchy.** Following [03-ECS](03.1-entity-component-system.md)'s
  own convention: every physics step is a plain function operating on a view
  of `Transform`+`Collider`(+`Rigidbody`), the same shape as the existing
  `MovementSystem`/`RenderSystem`, not a `Rigidbody` base class with virtual
  methods. What was originally imagined as one `PhysicsSystem` function ended
  up as five smaller ones — `GravitySystem`, `MovementSystem`,
  `DetectCollisions`, `ResolveCollisions`, `DispatchTriggerEvents` — plus
  `PhysicsUpdate` wiring them together in order, rather than one monolithic
  function: detection and response needed to be separable for tests that want
  deterministic collision behavior without gravity/movement noise, and
  `DispatchTriggerEvents` needed its own step since it's the only one that
  reads *last* frame's state (`PhysicsState`) as well as this frame's.
- **Trigger is a Collider property, not a second component.** A
  `ResolutionType` on the existing `Collider` (`Solid`/`Trigger`/`Unknown`)
  rather than a separate `TriggerVolume` component — the same
  `Transform`+`Collider` shape already drives detection either way, so a
  sensor volume only changes how an overlap is *responded to*, not what
  detects it.
- **Gravity as a constant force applied to the existing `Velocity` component**,
  not a second velocity field on `Rigidbody` — `Rigidbody` turned out to need
  only `m_Mass` and `m_AffectedByGravity`; duplicating `Velocity` inside it
  would have meant keeping two velocities in sync for no benefit.
  `GravitySystem` integrates into `Velocity.m_DY`, and `MovementSystem`
  already integrates `Velocity` into `Transform.m_Position` — reusing that
  step rather than building a second one.
- **`CollisionLayer` as a bitmask pair on `Collider`, not a second
  broadphase.** `m_Layer`/`m_Mask` are a cheap opt-out filter checked before
  the actual shape test, not a spatial partitioning scheme — still the same
  naive all-pairs `DetectCollisions` from the broadphase note below, just
  skipping pairs that were never going to interact (e.g. two independent
  "teams" of entities, a projectile that shouldn't hit its own owner).

## Tasks
- [x] Collision detection (`Collider` vs `Collider`, from
      [03-ECS](03.1-entity-component-system.md)'s existing component) —
      Rect and Circle shapes, every pairing — `math::AabbOverlap`/
      `CircleOverlap`/`PenetrationVector` (Collision.hpp) + `systems::DetectCollisions`
- [x] Gravity: constant acceleration applied to a `Rigidbody`+`Velocity`
      entity's `Velocity.m_DY` each frame — `systems::GravitySystem`
- [x] Collision response: basic resolution (stop/push out on overlap, split
      by mass ratio when both sides are movable) — not full impulse-based
      rigid body dynamics — `systems::ResolveCollisions`
- [x] Trigger colliders: a non-blocking `ResolutionType::Trigger` on
      `Collider` — never pushed out or pushes anything out; overlap fires
      `events::OnCollisionTriggerEnter`/`Stay`/`Exit` instead, for
      pickups/hazards/goal zones — `systems::DispatchTriggerEvents`
- [x] `PhysicsSystem` as a plain function, following `MovementSystem`'s
      existing shape — `systems::PhysicsUpdate`, wiring `GravitySystem`/
      `MovementSystem`/`DetectCollisions`/`ResolveCollisions`/
      `DispatchTriggerEvents` together in order
- [x] Selective collision via `CollisionLayer`: a `m_Layer`/`m_Mask` bitmask
      pair on `Collider`, checked mutually before any shape test — lets a
      pair of Colliders opt out of interacting with each other regardless
      of overlap — `components::details::LayersCanCollide` +
      `systems::DetectCollisions`

## Deliverables
- `PhysicsSystem` detecting AABB overlaps between entities with `Collider` —
  done (`systems::PhysicsUpdate`, wrapping `DetectCollisions`+`ResolveCollisions`)
- Gravity affecting any entity with `Rigidbody` — done (`systems::GravitySystem`)
- At least one example demonstrating a falling/colliding entity — done
  (`examples/physics_demo`)

## Explicitly out of scope for Phase 1
Continuous collision detection, raycasts, character controller
([Phase 2](../phase-2/07.2-physics-system.md)); soft body and vehicle physics
([Phase 3](../phase-3/07.3-physics-system.md)); broadphase beyond a naive all-pairs
check (revisit only if [13-Optimization](13.1-optimization.md) profiling shows it's
needed — no entity count in this engine justifies it yet).
